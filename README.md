# typst-engine

Typst 的**实时增量编译引擎** —— 一个 UI 无关的 Rust 库。

输入「正在编辑中的文本」，输出「排版好的文档 / 诊断」，全程在进程内完成：

- **不依赖 tinymist**，**不依赖 typst fork** —— 编译落点就是官方的 `typst::compile`
- **不依赖 tree-sitter** —— 语法树直接来自官方 `typst-syntax`
- **支持未保存内容** —— 通过覆盖式虚拟文件系统，编译器看到的就是你正在敲的文本

## 功能

### Typst 编辑（与 `wu` 对齐，但全部进程内）

| 功能 | `wu` 的做法 | 本项目的做法 |
|---|---|---|
| 实时编译预览 | 外部 `typst watch` 子进程 + PDF 轮询 | **进程内** `typst::compile`，敲键即重排 |
| 编译错误波浪线 | 跑 `typst compile --diagnostic-format short` | **进程内**，而且**不编译**就能先报语法错误 |
| 代码格式化 | 要求用户先装 `typstyle` 可执行文件 | **`typstyle-core` 进程内**，无安装前置 |
| 导出 PDF | 外部 `typst compile` | **`typst-pdf` 直接吃已排版的 `PagedDocument`** |
| 字数统计 | app 内的私有逻辑 | 引擎内，**有测试**（词数规则写清楚了） |
| 源码大纲 | 正则提取 `=` 标题 | `typst-syntax` 的 `ast::Heading`，可点击跳转 |
| 手动重编译 | 重启 watch | 作废源文件缓存后重编（把外部改动吃进来） |
| 编辑区 ↔ 显示区双向跳转 | 编辑区↔PDF 双向联动（SyncTeX 那套） | **双击任意一边**：编辑区点哪一行，预览跳到那一页；预览点哪一处，光标跳到那句话。靠排版结果里的**字形出处**，不需 SyncTeX、不重排版 |

### 界面：菜单条 · 目录树 · 右侧多视图

外壳向参考项目 `wu` 对齐（同一套 gpui / gpui-component rev，所以能照着搬）：

| 位置 | 内容 |
|---|---|
| 顶部菜单条 | **文件**（快速打开 / 保存 / 重新编译 / 导出 PDF / 退出）· **视图**（大纲 / 目录树 / 刷新 / 缩放） |
| 左栏 | 两个页签：**大纲**（本文件标题树）· **目录**（项目目录树，点文件即打开）· 右上角刷新 |
| 中间 | 工具栏 + 编辑器（原有） |
| 右侧 | 三个页签：**排版预览**（位图）· **Markdown** · **图片** |

目录树与「快速打开」共用同一份跳过规则（`tree::is_heavy_dir`）—— 否则会出现
「树里看不见、Ctrl+P 反而搜得到」。实测扫 `crates/engine/tests/fixtures`：
**2 个条目 / 0.2 ms**。

点目录树里的文件按类型分流（这就是「能展示图片、能渲染 markdown」的落点）：

- 图片（png/jpg/webp/gif/bmp/svg）→ 右侧图片视图（读文件在后台线程，解码在 UI 线程）
- `.md` → 右侧 **gpui-component 内置的 markdown 组件**：完整 GFM + 代码高亮，
  而且 `.selectable(true)` —— **显示区终于能选文字了**（排版预览是位图纹理，选不了）
- 其它文本 → 编辑器，右侧回到排版预览

相对 `wu` **没做**的：多标签（`tab_state.rs`）、项目搜索、术语表、最近文件、
PDF 反查（wu 走的是 `gpui-pdf` + 一个本地补丁，本项目自己的排版结果已经能双向跳转）。

### 长文档首屏：先让窗口出来，再排版

45 页冷编译原本是**同步**做的，就在 `cx.open_window` 的回调里 —— 于是窗口要
等排完才出现。现在首次排版**推迟到第一帧画完之后**（零延时计时器让出一轮
执行器），期间预览区显示「首次排版中…」。

实测（177 页 / 3000 行）：

```
首帧 @0 ms（窗口已画）
首次排版 @159 ms        ← 窗口已经出来了才开始排
首次排版完成：853.6 ms（177 页）@1020 ms
```

### `@preview` 包：本地目录 + 官方源

`#import "@preview/xxx:1.0"` 现在能联网取包。两条来源按序找：本地数据目录
（离线可用）→ 官方包源（`typst-kit` 的 `SystemPackages` + `SystemDownloader`，
ureq + 系统 TLS，不引 tokio）。下载落在 typst 自己的缓存目录
（`%LOCALAPPDATA%/typst/packages`），**与 CLI 共用一份**。

下载是**同步阻塞**在排版中间的，所以每次都把耗时报出来：

```
[typst-live] 取包 @preview/tablem:0.1.0：452.3 ms → C:\...\typst/packages\preview/tablem/0.1.0
[typst-live] 取包 @preview/tablem:0.1.0：0.0 ms   ← 同一个包的下一个文件，缓存命中
[typst-live] 首次排版完成：468.6 ms（1 页）
```

冷取 452 ms / 热取 0.1 ms。默认**不联网**（`Packages::local_only()`）：
离线要能编译本地项目，测试也不该碰网络。

### AI 编辑：选中文字 → Ctrl+K → 逐块确认

照 `wu` 的路子做，两处按本项目的取舍改了：

- **诊断不 shell 调外部 `typst`** —— 「语法检查并修复」的诊断来自 `typst-engine`
  自己（语法诊断 + 编译诊断），我们本来就有增量维护的语法树，不必再起进程
- **HTTP 走系统 `curl` 子进程**（`-N` 关缓冲跑 SSE）—— 不引 reqwest/tokio：
  AI 编辑是低频操作，几十毫秒的进程启动开销无所谓，而 tokio 是几 MB 依赖
  （Windows 10 1803+ 自带 curl；本地模型端点同样只需要 curl）

```
Ctrl+K            选中文字就改选区，没选就改整篇
输入一句要求  →   Enter
               →   右下角显示「已生成 N 字…」（思考模型的长思考也计入进度，Esc 可取消）
               →   逐块 diff 预览：+ 绿 / - 红
Enter 应用 · Tab/空格 切换本块 · ↑↓ 选块 · Esc 放弃
```

「AI」菜单里还有五个固定任务：语法检查并修复 / 中文校对 / 术语一致性 /
中译英 / 英译中。端点、模型、Key 从 `settings.conf` 的 `ai_base_url` /
`ai_model` / `ai_api_key` 读（环境变量 `AI_BASE_URL` / `AI_MODEL` /
`AI_API_KEY` 优先），默认端点 DeepSeek、默认模型 `deepseek-flash`。

三条实现上的硬要求，都写了测试：

| 要求 | 为什么 |
|---|---|
| **生成在 std 线程里跑，界面只轮询** | gpui 的 background_executor 池子里还跑着设置防抖、终端事件轮询等定时任务，一次 60 秒的 curl 会把它们一起饿死 |
| **`apply_hunks` 的行尾跟着原文** | 编辑器里是 CRLF，写死 `\n` 就会「AI 改一句、整篇行尾全变」（git 上等于全改） |
| **「全部拒绝」逐字节等于原文** | 连结尾多一个换行都算改了文件 —— 用户点拒绝就该什么都不发生 |

curl 的退出码翻译成人话再报（7 = 连不上端点 / 28 = 超时 / 35 = TLS / 60 = 证书），
直接报「退出码 7」等于没说。

### 标签页：多文件切换（切换时重编）

编辑区上方一条标签栏：文件名 + `×` 关闭，未保存的标签前面带 `●`。
点目录树的文件就在标签里打开；**已经开着的就切过去，不重读盘**
（这一条很关键：重读会把标签里未保存的改动冲掉）。关掉最后一个标签会留一个空的
`未命名.typ`，而不是把窗口关掉。

每个标签只存**最小状态**：路径、文本、未保存标记。视图状态（右栏模式、滚动位置）
与**排版结果都不按标签缓存** —— 切回来会重新编译：

```
[typst-live] 切标签 → hello.typ（0 ms，2 页）
[typst-live] 切标签 → 未命名.typ（19 ms，1 页）
```

这是**有意选的第一版**：引擎的入口（`EntryState` / `success_doc` / 源缓存）是单份的，
要让每个标签各自持有排版结果，得把引擎从「单入口」改成多入口 —— 那是真架构改动，
值得单独一轮。小文档切换 0–20 ms 感觉不到；45 页文档约 200 ms，会有一下顿感。

### 交互式终端（Ctrl+4）

底部面板，`Ctrl+4` 显隐（与 `wu` 同键位），标题栏带关闭按钮。跑的是真终端：
`alacritty_terminal`（Zed 同款终端核心，自带 pty）+ Windows 上的 PowerShell。

两处值得记的实现：

- **事件泵是自适应轮询**：有输出时 50 ms（回显跟手），连续空闲 2 秒后降到 120 ms。
  固定 50 ms 在空闲时是 20 Hz 常量唤醒，白烧 CPU；120 ms 上限又保证空闲后第一次
  敲键的回显延迟肉眼不可感 —— 这套是 `wu` 调出来的，照搬
- **调色板跟随应用主题**：浅色主题配 `TerminalPalette::light()`。ANSI 经典 X11 固定色
  （黄 `#CDCD00`）在近白底上对比度不到 1.5:1，基本看不清；程序若用真彩色直接指定
  颜色（纯黄 `#FFFF00`），`ensure_contrast` 会只调亮度、保住色相与饱和度

这个模块（`terminal.rs` + `terminal_view.rs` + `term_colors.rs`）是**整段搬 `wu` 的**：
同一套 gpui rev，所以 `cp` + 让编译器报错比「照着重写」快也更不容易走样。
`term_colors.rs` 是从 `wu` 的 `theme.rs` 里按函数边界摘出来的（那边 800 行是整套主题
系统，这里只要终端那一小块）。

验证（真窗口，自检向 pty 写命令再从网格读回）：

```
[typst-live] 终端已启动：powershell.exe
[selftest] @89ms   已向 pty 写入 echo 命令
[selftest] @2021ms 网格 14 行，读到命令回显？true
[selftest]   网格行："Windows PowerShell"
[selftest]   网格行："PS D:\...\fixtures> echo TERM_OK_MARK"
```

### 设置存在哪

`%APPDATA%\typst-live\settings.conf`（类 Unix 是 `$HOME/.config/typst-live/`）。
存窗口尺寸/位置、上次打开的文件、缩放、主题：

```
# typst-live 的设置。程序自己写，手改也认。
window=80,60,1320,880
file=crates/engine/tests/fixtures/hello.typ
zoom=1
theme=Default Dark
```

手写 `key=value`，没拉 serde —— 就这几项，解析/渲染当纯函数直接单测更便宜。
坏行、缺项、认不出的键一律跳过：**设置文件不该拦住程序启动**。

两个实测到的坑：

| 症状 | 根因 |
|---|---|
| 窗口每开一次就往下爬 11px | 存的是 `window.bounds()`（**客户区**）而不是 `window_bounds()`（下次开窗该用的那份几何） |
| 换了主题、磁盘上却没写 | 把「现在想要的」直接写进了「已经存盘的那份」，于是「变了才写」的比较永远相等。两者必须分开存 |

### 快捷键

编辑区上方是**工具栏：`wu` 那一整排都搬过来了**（26 个按钮 + 9 色下拉 + AI 下拉，
分 7 组用分隔条隔开，窄窗口横向滚）：

| 组 | 条目 |
|---|---|
| 字符 | B · I |
| 对齐 | 居左 · 居中 · 居右 |
| 段落与结构 | 两端 · 缩进 · 字体 · 标题 · 编号 · 题头 |
| 行内 | x² · x₂ · $ · `<>` · 删除线 · 高亮 · 引用 · • 列表 · 1. 列表 |
| 块 | 图片 · 图注 · 表格 · 分页 · 目录 · 链接 · 脚注 |
| 颜色 | 红橙黄绿青蓝紫灰黑（下拉） |
| AI | AI 编辑… + 五个固定任务（下拉） |

有选区就包住选区，没有就插空壳并把光标夹在中间（接着打就行）。逻辑在
`crates/app/src/markup.rs`，纯函数 + 单测 —— 中文选区按字节算不切半个字、
标题插**行首**而不是光标处，这两条都被测到了。

工具栏是**全宽一条**（在菜单条与主区之间），不是塞在编辑区里 —— 26 个按钮放进
520px 的编辑区必然溢出。每个按钮都 `flex_shrink_0`：flex 行默认会把超出容器的子项
**压得比文字还窄**，结果就是文字溢到邻居身上（看起来像「按钮重叠」），
和页框那次「被 flex 压扁」是同一个坑。

右侧主区**没有切换按钮**：视图由「现在在看什么文件」决定（打开 `.typ` 看排版预览、
`.md` 看 Markdown、图片看图片），与 `wu` 一致。非预览模式顶部只有一行纯文本标题，
说明在放什么。**排版预览里每页下方有页码**（当前页高亮显示「第 N 页 / 共 M 页」，
其余页只写 `N / M`），页码不随缩放变大小。

**状态栏是一行，贴窗口最底**：引擎指标（排版/光栅化/索引耗时、重解析字节、
纹理 MiB、页码、缩放、三个计数）+ 文档统计（字/词/行）+ 标题数 + 保存状态 +
错误数 + 一次性消息 + 主题下拉。左侧指标放在 `flex_1 + overflow_hidden` 的容器里
（窄窗口下宁可裁掉几个数字），**右侧的消息与主题下拉是固定的**，永远看得见。

| 快捷键 | 功能 |
|---|---|
| `Ctrl+P` | **快速跳转**：按文件名/路径片段模糊搜项目内文件，↑↓ 选、Enter 开、Esc 取消 |
| `Ctrl+S` | 保存当前文件（写盘后撤掉内存覆盖层） |
| `Ctrl+B` | 手动重新编译（作废源文件缓存，把外部改动吃进来） |
| `Ctrl+Shift+F` | 格式化（进程内 typstyle） |
| `Ctrl+E` | 导出 PDF（到同名的 `.pdf`） |
| `Ctrl+=` / `Ctrl+-` / `Ctrl+0` | 预览缩放 放大 / 缩小 / 100% |
| `Ctrl+滚轮` | 预览缩放（缩完把当前页锚回顶部） |
| `PageUp` / `PageDown` | 预览上一页 / 下一页 |
| `Ctrl+Home` / `Ctrl+End` | 预览首页 / 末页 |
| **双击编辑区** | 光标所在处 → 预览对应位置 |
| **双击预览** | 那一点 → 编辑区光标 |
| **Ctrl+单击预览** | 点在链接上就用浏览器打开（不能直接单击：双击跳转的**第一次点击**也会先报一次单击） |

| 点大纲条目 | 光标跳到那一行 |

### 快速跳转的打分规则

子序列匹配（字符按序出现即可，不要求连续），在此之上按「像不像用户想要的」加分：

| 加分 | 条件 | 理由 |
|---|---|---|
| +1 | 每个命中字符 | 基础分 |
| +8 | 与上一个命中相邻 | `util` 命中 `util.rs` 优于命中 `u_t_i_l.rs` |
| +6 | 命中在词边界（`/ _ - . 空格` 后，或大小写切换处） | `util` 命中 `src/util.rs` 优于命中 `src/xutil.rs` |
| +4 | 命中在**文件名**部分 | 搜 `util` 时 `src/util.rs` 应排在 `util/x.rs` 前 |

同分按路径字典序 —— 次序必须确定，否则用户会觉得列表在「乱跳」。

### 没有对齐 `wu` 的部分（不是说做不到，是判断不值得）

`wu` 还有目录树、多标签、项目搜索、快速打开、最近文件、术语表、Markdown 预览、
图片查看、**交互式终端**、**AI 诊断/对话改稿**。

这些要么是重建 `wu` 的整个外壳（而本项目的价值在引擎），要么与「实时编译」这个核心无关。
把引擎做扎实、把 Typst 编辑本身做好，比再做一个 `wu` 有意义。

## 跑起来看

```bash
cargo run -p typst-live                # 开窗，用内置示例文档
cargo run -p typst-live -- doc.typ     # 开窗，打开指定文件
```

左边是带 Typst 语法高亮的编辑器，右边跟着实时更新。状态栏那几个数字就是
「实时」的证据：排版耗时 / 光栅化耗时 / 重解析字节 / 页数 / 缩放 / 排版与光栅化次数。

*Ctrl+=* 放大、*Ctrl+-* 缩小、*Ctrl+0* 回到 100%。

```bash
cargo run --example realtime   # 不开窗，在终端里跑逐字输入的性能数据
```

## 实测

300 段中文文档（34 KB / 9 页 A4），逐字输入：

```
字体冷启动（扫系统字体）：  67.6 ms   ← 只做一次
冷编译（全量）：           191.1 ms
平均每次敲键：  重解析 276 字节（占全文 0.80%），编译 1.9 ms
对比冷编译：增量快 102.6×
30 次敲键累计 55.9 ms，而全量重编需要 5732.4 ms
```

> **一个值得记下来的 gpui 坑**：`Window::dispatch_action` 是**从当前聚焦节点**
> 开始沿 dispatch path 上溯的（`window.rs:1992`）。如果窗口里**没有任何节点有焦点**，
> 动作派发就没有起点 —— `on_action` 的处理函数永远不会被调用，
> **所有全局快捷键静默失效**。本应用初版就中了这一条：启动后没给编辑器设焦点，
> 于是必须先点一下编辑器才能打字，而且在那之前 Ctrl+S 之类全都没反应。
> 修法是启动时 `state.focus(window, cx)`。

### L4：做了大纲与波浪线，没做高亮（附理由）

`typst_syntax::highlight()` 是现成的，但 **gpui-component 的编辑器把高亮焊死在
tree-sitter 上**（`LanguageConfig.language` 是硬字段，`SyntaxHighlighter` 是具体结构体
而非 trait），没有注入点。要用官方语法树着色就得 fork gpui-component —— 代价不成立。
所以**不写没有消费方的代码**，编辑器高亮继续走 tree-sitter。

交付的是有真实消费方的两样：**左侧大纲栏**，以及**编辑器的红/黄波浪线**
（语法错误不编译就有，编译错误同样映射成一种形状）。

一个真 bug 由此被测试揪出：大纲初版把「751 个标题 × 51 KB」算成了 O(n²)，
实测 **106 ms**（一次敲键合计 116 ms，远超一帧）。改成一次性建行首索引后 **1.1 ms**。

### 双击双向跳转：靠排版结果里的字形出处

不需要 SyncTeX，也不需要第二个辅助文件。typst 的排版结果里本来就有源码位置：

```rust
typst::layout::TextItem { glyphs: Vec<Glyph { span: (Span, u16), .. }>, .. }
//                                       ~~~~  ~~~~~~~
//                                      哪个语法节点   节点内的字节偏移
```

所以遍历一次 `Page.frame`（带 `Group` 递归与仿射变换）就能把「每个字形画在哪」
与「它来自源码哪几个字节」对应起来，存成一张 `byte ⇄ 页/页内 pt` 的表
（`crates/engine/src/jump.rs`，UI 无关，可单测）。

**它凭空多出一层，而且这层天生与缩放无关：**

```
排版 (PagedDocument, pt)  ──►  跳转索引 (byte ⇄ 页/页内 pt)  ──►  光栅化 (纹理)
      每次敲键                     跳转时惰性建一次，之后复用           缩放/滚动时
```

坐标全部用 pt（不是像素），索引也不是每次敲键都建 —— 它按**排版结果的 `Arc` 指针**
缓存。于是「缩放不会重建索引」变成一条可以直接在状态栏上读到的断言：
按 `Ctrl+=` 时只有「光栅化」在涨，「排版」与「索引」都不动。

实测（3000 行 / 45 页中文文档，debug 构建，引擎自身未优化）：

```
字形数               20449
建索引               22.3 ms   ← 只在“改完字之后第一次跳”时付一次
前向查找              2.1 µs
反向查找              4.2 µs
```

命中策略（都写进了测试）：

| 情况 | 行为 |
|---|---|
| 光标所在字节真有字形 | 精确命中那**一个字**（高亮框只盖一个字） |
| 光标在 `#set` / 注释 / 未渲染的代码里 | **就近吸附**到源码上最近的字形（平手时取**靠前**的：刚敲完回车，人想看的是上面那段） |
| 双击处的文字在页眉等多处重复 | 取**页号最小、页内最靠上**的那个（次序确定） |
| 双击在页边距 / 图上 | 吸附到**本页**最近的文字；只要这页有字就不会没反应 |
| 编译失败期间 | **跳转直接关掉**（预览留在屏幕上是旧结果，源码已变，字节偏移对不上 —— 宁可说“现在跳不了”） |

#### 这条链路上踩过的坑

| 症状 | 根因 | 修法 |
|---|---|---|
| **预览滚过之后，双击位置整页偏** | `ScrollHandle::bounds_for_item` 给的是**内容坐标**（`top_item` 用的也是这一套），不是窗口坐标 | 加上滚动偏移；`window_to_page_pt` / `page_pt_to_window` 互为正反函数 |
| 中文文档一建索引就 panic | `Span` 里那个 `u16` 偏移可能落在**一个字符的中间**，`&text[..end]` 直接炸 | 对齐到字符边界（取该字符完整范围） |
| 高亮框上下颠倒 / 偏高一行 | 文本空间 y **向上**，帧空间 y **向下** | 上升量取负（`-y_offset`），上边界 `-asc`、下边界 `+desc` |
| 旋转 / `place` 里的文字位置差很远 | 变换的复合顺序必须与 `typst-render` 完全一致 | 复刻 `pre_translate` / `pre_concat` 的顺序（`acc ∘ 平移 ∘ 组变换`） |
| 跳转到错的行 | 排版失败时索引还在用新源码的偏移 | 每次 `recompile` 作废索引，失败期间禁用 |

#### 怎么验证“双击真的跳对了”

gpui **不接受注入的键盘/鼠标输入**（`SendKeys` 无效，见 `docs/NEXT.md`），所以
端到端只能让程序自己走一遍真代码路径并**把数字报出来**。本次验证临时加了一段
「按帧号推进」的自检（走完就删了），它模拟了两次双击：

```
[selftest] ① 前向：先滚到 y=-1200px，光标置于字节 583（第 23 行），触发跳转
[typst-live] 建跳转索引：6 页 / 190 个字形，用时 0.1 ms（第 1 次）
[typst-live] 前向跳转：第 23 行（字节 583）→ 第 6 页，页内 y=69.0 pt
[selftest] ② 目标行现在画在窗口 y=142.7px（期望 142.7px）—— ✓ 前向滚动对位
[selftest] ② 跳到第 6 页；gpui 自己算出的可见页首项 = 6
[selftest] ③ 反向：模拟双击窗口 Point { x: 884.6px, y: 150px } → 页内 (185.98, 74.48) pt
[typst-live] 反向跳转：第 6 页 (186.0, 74.5) pt → 第 23 行（字节 583..586）
[selftest] ✓ 往返闭环
[selftest] ④ 缩放后索引仍为 1 次 —— ✓ 索引与缩放无关
```

重点是：即使调试时预览已经滚到第六页（偏移 -5745px），双向也能回到**同一个字**
（字节 `583..586`）。前面那个「内容坐标 / 窗口坐标」的坑就是靠第二行断言
（“目标行现在画在窗口 y=……”）揪出来的 —— 不带滚动偏移时，反向双击会偏出整页。

引擎侧另有一条更强的性质测试（`tests/jump.rs`）：对正文抽样，
`inverse(forward(b)) == b` 必须逐字相等，不是“差不多同一行”。

#### 已知取舍（写在模块头里）

- **旋转/倾斜内容**：字形框取四角变换后的**外接框**，所以是近似
- **别的文件**（`#include`）里的内容：span 指向的不是主文件，跳过不跳
- **图形/图片/线**：不建索引，落在它们身上时走「吸附到本页最近的文字」
- **链接**：单独存一份矩形（`LayoutIndex::links()`），外壳用 Ctrl+单击打开。
  只支持网址 —— 文档内部的 `Location` 链接会提示「暂时打不开」

### 预览：位图，不是 SVG

初稿打算用 SVG 做预览，实测后否掉：一页 15cm 中文文档的 SVG 是 493 KiB，而 gpui
固定按自然尺寸 **×2** 光栅化，且纹理缓存键是**内容哈希** —— 改显示尺寸拿不到更高分辨率，
缩放必然糊，还把 1.5 MiB 的页面放大成 5.24 MiB 纹理。

改用 `typst-render` 自己出图后：DPI 完全由我们决定，而且能**同步**构造 `RenderImage`，
绕开 gpui 的异步 asset 系统。

由此确立的关键分层：**排版与光栅化是两层**。缩放只重做出图，不重新排版 ——
状态栏的「排版 N 次 / 光栅化 M 次」会直接把这件事显示出来。

### 纹理按视口惰性出图（不这样做会爆）

实测：**A4 单页在 100% 缩放下就占 7.7 MiB 纹理**（`height: auto` 的短页约 3.4 MiB）。
100 页全量常驻就是 **770 MiB**；400% 时每页 54 MiB，直接爆。

现在只保留**可见范围 ± 1 页**的纹理：

```
初始      视口 1–2 页：新出图 2，常驻 2 页 15.3 MiB     ← 不是 10 页 76.5 MiB
LastPage  视口 9–10： 新出图 2，卸载 2，常驻 2 页
NextPage  视口 2–4：  新出图 1，卸载 1，常驻 3 页        ← 滑动窗口，不重出
```

常驻纹理稳定在 2–3 页，**不随文档长度增长**。100 页从 770 MiB 降到约 23 MiB。

关键实现细节：**布局尺寸用 `page_sizes`（由 pt 算出），不用纹理像素**。
这样某一页没出图时页面尺寸也不变 —— 否则滚动条会在滚到新页的瞬间跳一下，
而且翻页 / 跳大纲都会错位（它们直接依赖页框位置，不需要页已出图）。

可见范围直接来自 gpui 的 `ScrollHandle::top_item()` / `bottom_item()`
（我们的滚动子项恰好就是页）。**只在可见范围真的变了**才重新同步，
否则滚动过程中每帧重算会发涩。

#### ⚠️ 页框必须 `flex_shrink_0`，否则滚轮根本滚不动

这条踩过坑。加视口逻辑后日志立刻报出异常：布局后视口居然「看到」全部 10 页。

根因：flex 列容器默认 `flex-shrink: 1`，会把超出视口高度的页**压缩进视口** ——
结果是容器永远不会溢出，**滚轮因此没有任何东西可滚**，
而且视口光栅化会误以为全部页可见、把纹理全出出来。

这是「为了做 A 而写的诊断抓到了 B 的根因」：滚轮「不工作」不是事件没送到，
而是根本没有可滚的内容。页框加上 `.flex_shrink_0()` 后两者一起好了。

### ⚠️ 光栅化必须把显示器的 DPI 缩放算进去

这条踩过坑，而且症状是「看着不清晰」这种容易被当成观感问题放过的。

**事实**：gpui 的布局用**逻辑像素**，物理像素是它的 `scale_factor` 倍
（`window.scale_factor()`）。本机面板 2560×1600、Windows 缩放 150%，
所以 `scale_factor = 1.50`。

若按 96 dpi 出图：一页 15cm = 425.2pt → 567 物理像素，
而它要占满 850 物理像素（567 逻辑 × 1.5）—— **被拉伸 1.5 倍，必然发虚**。

```
出图： pixel_per_pt = BASE(96/72) × zoom × scale_factor    → 1.33 × 1.5 = 2.00 px/pt
布局： 逻辑尺寸   = 纹理物理像素 / scale_factor              → 850 / 1.5 = 566.67
```

应用自报的实测：纹理 850×1050 物理px → 布局 566.67×700 逻辑px →
屏幕 850×1050 物理px —— **与纹理完全 1:1**。

> 注意**页面尺寸没变**：旧算法也是 850 物理像素（567 逻辑 × 1.5）。
> 所以 100% 依然是「实际大小」，变的只是纹理分辨率。
> 判断「修没修好」应该看**纹理像素与屏幕物理像素是否 1:1**，不是看字变大没变大。

另外 `RenderImage.scale_factor` 是 `pub(crate)`，我们改不了（gpui 自己的
SVG 渲染器就是靠设它来处理同一件事），所以只能在出图与布局两端自己算。

**代价**：纹理 1.5 → 3.4 MiB（1.5² = 2.25 倍），光栅化 1 → 3.5 ms。
这让高倍缩放下的显存更值得关注（400% 时每页约 54 MiB）。

**显示器切换**：窗口被拖到另一块缩放不同的屏上时，`render` 里发现
`scale_factor` 变了就重新出图 —— 否则要么糊、要么白费显存。

cargo run -p typst-live       # 开窗的实时预览器

## 设计依据

来自对 [tinymist](https://github.com/Myriad-Dreamin/tinymist) 编译链的**源码级拆解**。
采用了它的 overlay VFS、revision 失效、comemo 记忆化、`success_doc` 失败保留、
`TypeId` 键导出计算图、actor 单写者队列；砍掉了它为本项目不需要的东西
（LSP、多项目锁库、浏览器目标、typst fork、自研字体与包解析、`rpds`）。

其中三条最关键的结论是实测官方源码得出的，与直觉相反：

1. **`typst::compile` 就是全部** —— tinymist 的 `typst-shim` 只包了一个 `SYNTAX_ONLY` 开关
2. **fork 只为分析层** —— 编译路径完全不需要它
3. **typst 自带增量重解析**（`Source::replace` / `edit`）—— 这是「实时」的正解，
   而且它**返回实际重解析范围**，让增量有效性变成可直接断言的数字
